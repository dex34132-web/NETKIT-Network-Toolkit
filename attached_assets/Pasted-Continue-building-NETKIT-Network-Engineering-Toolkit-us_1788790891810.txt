Continue building **NETKIT — Network Engineering Toolkit** using the existing design system and architecture as the source of truth. Add two production-quality tools: **VLAN Calculator** and **Port Reference**. Preserve NETKIT's clean, minimal, professional engineering aesthetic: dark navy/charcoal surfaces, restrained blue accents, subtle borders, compact but comfortable spacing, crisp typography, clear information hierarchy, and highly readable technical tables. Do not introduce marketing sections, unnecessary decoration, fake statistics, birthday messages, excessive animations, or generic dashboard filler. Both tools must be useful for real network-engineering workflows, work entirely client-side, function offline, and share reusable components with the existing NETKIT tools.

**VLAN CALCULATOR:** Build this as a practical VLAN and subnet-planning workspace. Allow the user to enter a base IPv4 network/CIDR, VLAN ID, VLAN name/description, and desired subnet configuration. Support calculating subnet details associated with a VLAN, including VLAN ID, VLAN name, network address, CIDR prefix, subnet mask, wildcard mask, first usable host, last usable host, broadcast address, total addresses, usable hosts, and address range. Provide an optional VLAN planning table where engineers can create multiple VLAN entries and assign each one a VLAN ID, name, network/CIDR, purpose, gateway, and host requirement. Validate VLAN IDs using standard 802.1Q ranges, clearly distinguish normal VLAN IDs from the extended range, prevent duplicate VLAN IDs, detect overlapping subnet assignments between VLANs, and flag invalid or conflicting configurations. When planning from host requirements, calculate an appropriate subnet size and clearly show how many usable addresses remain. Include copy, edit, delete, duplicate, reset, and export functionality. Make conflicts highly visible but calm: for example, clearly identify duplicate VLAN IDs or overlapping IP networks without overwhelming the interface. The result should function as a lightweight VLAN planning tool rather than merely a subnet calculator with the word “VLAN” added to it.

**PORT REFERENCE:** Build a fast searchable reference database for common networking ports and protocols. The primary interface should be a highly usable table with columns such as **Port, Protocol, Service, Transport, Description, Common Usage, and Notes**. Include common TCP, UDP, and TCP/UDP services and organize them logically rather than presenting an enormous wall of entries. Provide instant search that can match port numbers, protocol names, service names, and keywords; filters for TCP, UDP, TCP/UDP, and common categories; sorting; and a detailed information panel when a port is selected. Include useful categories such as remote access, web, DNS, email, file transfer, directory/authentication, monitoring, databases, and network management. Clearly distinguish well-known ports from registered/dynamic ranges and avoid implying that a port number alone guarantees a particular service. Add a quick lookup field where an engineer can enter something like `443`, `SSH`, or `DNS` and immediately receive the relevant entries. Every row should have a copy action so the port number, protocol, or a concise reference can be copied quickly. Include a small “Port Range” reference explaining 0–1023, 1024–49151, and 49152–65535, while keeping the main experience focused on fast lookup rather than turning it into a networking textbook.

**UX, DATA QUALITY & INTEGRATION:** Both tools must feel native to NETKIT and use the same sidebar, header, cards, inputs, dropdowns, buttons, tables, status indicators, typography, responsive behavior, and theme system as the existing CIDR Calculator, Subnet Calculator, IP Tools, and IP Range/Overlap Checker. Keep calculation and validation logic separate from UI components and make the VLAN calculations independently testable. Store VLAN planning data locally so it survives page refreshes without requiring an account or backend, while allowing users to clear/reset it. For Port Reference, use a structured local dataset rather than an external API so the tool remains fully offline. Include proper empty states, validation errors, confirmation states where destructive actions are involved, loading-free instant interactions, keyboard navigation, focus states, and responsive behavior for smaller screens. Do not fabricate technical information: use accurate standard/common port assignments and clearly label entries where a service association is commonly used rather than universally guaranteed. The final result should feel like a tool a professional network engineer could bookmark and genuinely use during network design, troubleshooting, documentation, or configuration work.
