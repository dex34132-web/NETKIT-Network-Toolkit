You are building two production-quality networking tools inside **NETKIT — Network Engineering Toolkit**, an offline-first web application designed for professional network engineers. The existing NETKIT design system must be preserved: dark navy/charcoal interface, subtle glass-like surfaces, restrained blue accents, crisp typography, rounded cards, thin borders, excellent spacing, clear hierarchy, and zero unnecessary decoration. The tools must feel like serious engineering utilities rather than educational demos. Prioritize clarity, speed, accuracy, keyboard-friendly interaction, responsive layouts, and readable technical data. Do not add marketing copy, birthday messages, fake metrics, unnecessary animations, or decorative elements. Every number displayed must be calculated from the user's actual input; never use hardcoded fake results. The application must work entirely client-side and remain usable offline.

**SUBNET CALCULATOR:** Build a complete subnetting workspace rather than a single calculator field. The user should be able to enter a base IPv4 network/address and choose a target subnet prefix or specify the desired number of subnets/hosts, with intelligent validation and clear error messages. After calculation, present a highly readable results workspace showing the original network, original CIDR, subnet mask, wildcard mask, total addresses, usable hosts, number of generated subnets, new prefix, and address increment. Display every generated subnet in a sortable table containing subnet number, network address, first usable address, last usable address, broadcast address, CIDR prefix, subnet mask, and usable-host count. Add controls for copying individual rows, copying the entire table, and exporting results. Include a compact visual representation of the address space so the user can immediately understand how the original network was divided. Support valid IPv4 prefixes from /0 through /32, correctly handle edge cases such as /31 and /32 according to modern IPv4 addressing conventions, prevent invalid host/subnet combinations, and make the distinction between network, broadcast, and usable addresses explicit. Results should update cleanly without cluttering the screen.

**IP RANGE / OVERLAP CHECKER:** Create a dedicated comparison workspace where users can enter two or more IPv4 addresses, CIDR networks, or explicit start/end IP ranges. The tool must normalize each input into a precise numerical address range and then determine whether ranges overlap, touch, are completely separate, contain one another, or are identical. For each range, display the normalized network/start address, end address, CIDR when applicable, subnet mask when applicable, total address count, and relationship to the other ranges. The primary result should be visually obvious: use a large, calm status panel such as “No Overlap”, “Partial Overlap”, “Range A Contains Range B”, “Range B Contains Range A”, or “Identical Ranges”, accompanied by a concise explanation. When an overlap exists, calculate the exact overlapping address range and number of overlapping addresses. Support multiple-range comparison so engineers can paste several networks and quickly detect conflicts. Include a visual horizontal range representation where appropriate, but never let visualization replace the exact numerical results. Add copy/export controls and useful validation for malformed IPs, reversed ranges, duplicate ranges, mixed CIDR/range formats, and IPv4 values outside 0.0.0.0–255.255.255.255.

**UX, ENGINEERING QUALITY & INTEGRATION:** Both tools must share the exact same NETKIT navigation, header, typography, controls, cards, buttons, inputs, tables, status indicators, responsive behavior, dark/light theme system, and offline-ready architecture as the rest of the application. Use reusable components instead of duplicating UI code. Keep calculations deterministic, mathematically correct, and independent of external APIs. Separate calculation logic from presentation so the networking algorithms can be tested independently. Add thorough input validation and graceful empty/error states rather than allowing broken or misleading results. Preserve user inputs during navigation where practical, provide keyboard navigation and sensible focus states, and make tables usable on smaller screens without destroying readability. The finished experience should feel like a professional engineer opened NETKIT during a real troubleshooting or network-design task and immediately knew exactly where to enter data, what the result means, and how to copy it into documentation or a configuration workflow.
