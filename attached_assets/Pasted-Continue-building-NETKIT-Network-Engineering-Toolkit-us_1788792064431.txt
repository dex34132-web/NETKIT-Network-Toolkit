Continue building **NETKIT — Network Engineering Toolkit** using the existing application architecture and visual design system as the single source of truth. Add two production-quality tools: **Command Builder** and **Notes**. Both must feel like native parts of the same professional network-engineering application. Preserve the established clean, minimal dark interface: dark navy/charcoal surfaces, restrained blue accents, subtle borders, crisp typography, compact information-dense layouts, excellent spacing, and clear hierarchy. Do not add marketing sections, fake metrics, decorative cybersecurity graphics, birthday messaging, or unnecessary animations. Prioritize practical workflows, fast interaction, keyboard accessibility, local/offline operation, and safe handling of generated configuration. Reuse existing components wherever possible instead of creating a separate design language.

**COMMAND BUILDER:** Create a structured configuration-generation workspace where an engineer selects a **vendor/platform**, **command category**, and required parameters, then receives a clearly formatted, copy-ready command/configuration block. Start with practical vendor categories such as Cisco IOS/IOS-XE, Juniper Junos, FortiGate, Palo Alto Networks, and F5 BIG-IP, but structure the system so additional vendors and command templates can be added later without rewriting the UI. Organize templates into useful categories such as interface configuration, IP addressing, VLANs, static routes, routing protocols, access/control policies, diagnostics, and show/display commands. Instead of forcing users to write commands manually, dynamically generate forms based on the selected template: for example, interface name, IP address, prefix/mask, VLAN ID, gateway, description, protocol, route destination, next hop, and other template-specific parameters. Show the generated configuration in a professional monospace code panel with line numbers, syntax-friendly formatting, a one-click Copy button, and an option to download/export the configuration as plain text. Include Reset, Edit Inputs, and Regenerate controls. Validate inputs before generating commands and clearly flag missing or potentially invalid values. Never claim that generated commands are universally safe or compatible with every device/version; display a subtle “Review before applying” indication. Keep vendor syntax isolated inside structured templates so the UI and business logic remain maintainable. The Command Builder should feel like a reliable configuration assistant, not an AI chatbot.

**NOTES:** Build a lightweight but genuinely useful engineering notes workspace designed for documenting network work. Users should be able to create, edit, search, pin, duplicate, archive, and delete notes entirely offline using local browser storage. Each note should support a title, optional category, tags, timestamps, and a rich but intentionally restrained editor suitable for technical documentation. Support practical formatting such as headings, bold/italic text, bullet lists, numbered lists, checklists, inline code, code blocks, and simple tables. Make code blocks especially useful for storing commands and configuration snippets, with a copy button directly inside each code block. Provide categories such as Network Design, Troubleshooting, Commands, IP Planning, VLANs, Devices, and General, while allowing custom categories/tags. The notes list should have instant search and filtering by category, tag, pinned status, and recently updated notes. Selecting a note should open a focused editor rather than forcing the user through unnecessary dialogs. Include autosave with a clear saved-state indicator, manual save where appropriate, duplicate-note functionality, and safe confirmation before permanent deletion. Provide import/export functionality using a simple local format so notes can be backed up and moved between machines. Do not require authentication, a database, or an internet connection.

**UX, ARCHITECTURE & SAFETY:** Both tools must integrate seamlessly with the existing NETKIT navigation and responsive layout. Command Builder should prioritize a three-part workflow — **Select Template → Configure Parameters → Review & Copy Output** — while Notes should prioritize **Find → Read/Edit → Save**. Keep primary actions visually obvious without turning every element into a large button. Use contextual validation directly beside problematic fields, preserve entered values when switching between compatible options, and provide useful empty states instead of blank screens. All command generation must be deterministic and template-based; do not invent configuration syntax dynamically. Keep vendor templates, validation rules, note models, storage logic, and UI components separated cleanly so OpenCode can extend and test them later. Add keyboard shortcuts where they genuinely improve productivity, including search, save, copy, and creating a new note. Ensure the application remains fast with hundreds of locally stored notes and many command templates. The finished experience should feel like a professional engineer's personal utility workstation: select what you need, enter the minimum information, get a precise result, copy or save it, and move on.
